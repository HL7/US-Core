* **USCDI-related Updates**: We have updated US Core to include the new [U.S. Core Data for Interoperability (USCDI) v7](https://www.healthit.gov/isa/united-states-core-data-interoperability-uscdi#uscdi-v7) Data Elements and Classes that the  Office of the National Coordinator for Health Information Technology (ONC) published.  USCDI v7 includes 30 new data elements and one significantly revised data element (Tobacco and Nicotine Product Use, an evolution of the Smoking Status data element) for a total of 31 overall new data elements across multiple data classes:

  * Of the 31 overall new data elements, the following 14 data elements are already represented in in US Core as *Must Support* or *Additional USCDI* elements, and no changes were introduced in this version:

  * For the USCDI Allergy Intolerance Criticality data element, we added `AllergyIntolerance.criticality` to the [US Core AllergyIntolerance Profile](StructureDefinition-us-core-allergyintolerance.html) as an *Additional USCDI* element.

  * For the USCDI Healthcare Agent data element, we added guidance to the [US Core CareTeam Profile](StructureDefinition-us-core-careteam.html) and the [US Core RelatedPerson Profile](StructureDefinition-us-core-relatedperson.html) on recording the person legally authorized to make healthcare decisions for a patient. `CareTeam.participant.role` is bound to a new US Core value set that adds the durable power of attorney (DPOWATT), healthcare power of attorney (HPOWATT), and Patient Healthcare agent (LOINC 81335-2) codes to Care Team Member Function, and the `RelatedPerson.relationship` binding strength is raised from *preferred* to *extensible*. **Note that the US Core Care Team Member Function value set is pending authoring in VSAC. Until it is published, `CareTeam.participant.role` is bound to a placeholder value set that does not resolve, and validation reports that the value set cannot be found.**

  * For the USCDI Referral Note data element, we added Referral Note (LOINC 57133-1) to the ["Common Clinical Notes" list](clinical-notes.html#clinical-notes) on the Clinical Notes guidance page and to the [US Core Clinical Note Type](ValueSet-us-core-clinical-note-type.html) value set, raising the minimum set of note types servers support from ten to eleven.

  * For the USCDI Tobacco and Nicotine Product Use data element, which USCDI v7 renamed and broadened from Smoking Status, we renamed the US Core Smoking Status Observation Profile to the [US Core Tobacco And Nicotine Use Observation Profile](StructureDefinition-us-core-smokingstatus.html) and updated its description for the expanded scope. The value sets bound to `Observation.status`, `Observation.code` and `Observation.value[x]` have also been renamed to [US Core Tobacco And Nicotine Observation Status](ValueSet-us-core-observation-smoking-status-status.html), [Tobacco And Nicotine Use Status](https://vsac.nlm.nih.gov/valueset/2.16.840.1.113762.1.4.1267.6/expansion), and [Tobacco And Nicotine Use](https://vsac.nlm.nih.gov/valueset/2.16.840.1.113762.1.4.1267.3/expansion).  **Note that the review to add codes to those value sets for broader tobacco and nicotine coverage is pending in VSAC.**

  * For the USCDI Nutrition Assessment data element, we added guidance to the [Screening and Assessments](screening-and-assessments.html#nutrition-assessment) page on recording nutrition assessments using the existing Screening and Assessments framework, and added a new category code, "nutrition-assessment", to the [US Core Category](CodeSystem-us-core-category.html) code system and to the [US Core Screening Assessment Observation Category](ValueSet-us-core-screening-assessment-observation-category.html) value set, the minimum set of category codes servers support for the USCDI Health Status Assessments data class. **Note that the terminology for this data element is still pending a decision. The new [US Core Nutrition Assessment](ValueSet-us-core-nutrition-assessment.html) value set is a placeholder containing the panel items of the LOINC Nutrition assessment panel (75282-4) and is expected to change.**

  * For the USCDI Reason Not Performed data element, we:
    *  added `Procedure.statusReason` to the [US Core Procedure Profile](StructureDefinition-us-core-procedure.html) as a *Must Support* element, and preadopted the FHIR R5 `Procedure.recorded` element as a cross-version extension and an *Additional USCDI* element.
    *  raised the binding strength of `Immunization.statusReason` on the [US Core Immunization Profile](StructureDefinition-us-core-immunization.html) from *example* to *extensible*.
    *  raised the patient + status combination search API conformance to **SHALL** for both profiles.
    *  The [US Core MedicationAdministration Profile](StructureDefinition-us-core-medicationadministration.html) is also in scope for this data element and is addressed in the USCDI Medication Administration data element below.

    **Note that the bindings are provisional, pending the review of the terminology aligned with the HL7 FHIR US Quality Core Implementation Guide.**

  * For the USCDI Specimen Collection Date and Time and Specimen Collection Method data elements, we added `Specimen.collection.collected[x]` and `Specimen.collection.method` to the [US Core Specimen Profile](StructureDefinition-us-core-specimen.html) as *Additional USCDI* elements. Note that `Observation.effective[x]` on the [US Core Laboratory Result Observation Profile](StructureDefinition-us-core-observation-lab.html) is already a *Must Support* element and also maps to Specimen Collection Date and Time. `Specimen.collection.method` has a *preferred* binding to the [Specimen Collection Method](https://vsac.nlm.nih.gov/valueset/2.16.840.1.113762.1.4.1267.44/expansion) value set in VSAC, which replaces the interim binding to the FHIR Specimen Collection Method value set, and implementer guidance states that `Specimen.collection.method` is used when the collection method is not conveyed by `Specimen.type`, and that when both fields are populated the method code **SHOULD** be consistent with or more specific than the type code.

  * For the USCDI Referral Order data element, we added Patient referral (procedure) (SNOMED CT 3457005) to the [US Core ServiceRequest Category Codes](ValueSet-us-core-servicerequest-category.html) value set and added guidance to the [US Core ServiceRequest Profile](StructureDefinition-us-core-servicerequest.html) recommending it as the `ServiceRequest.category` code for referral orders. The `ServiceRequest.code` binding remains unconstrained, as it is for the USCDI Procedure Order data element.

  * For the USCDI Appointment data element, we added a new [US Core Appointment Profile](StructureDefinition-us-core-appointment.html) that sets minimum expectations for recording, searching, and fetching a healthcare event scheduled for a past, current, or future date and time. `Appointment.identifier`, `Appointment.status`, `Appointment.serviceType`, `Appointment.start`, `Appointment.end`, `Appointment.participant.type`, `Appointment.participant.actor`, and `Appointment.participant.status` are *Must Support* elements, and the [US Core Patient Profile](StructureDefinition-us-core-patient.html), [US Core Practitioner Profile](StructureDefinition-us-core-practitioner.html), and [US Core Location Profile](StructureDefinition-us-core-location.html) are *Must Support* `Appointment.participant.actor` targets. The Location target also conveys the facility where the scheduled event is to take place. We also added `Encounter.appointment` to the [US Core Encounter Profile](StructureDefinition-us-core-encounter.html) as an *Additional USCDI* element so an encounter records the appointment that scheduled it. **Note that the `Appointment.serviceType` binding is *example*, since appointment service types are typically drawn from a local service catalog. It names the IHE Scheduling profile's SNOMED CT services value set, which is not published in a package US Core depends on, so validation reports that the value set cannot be found.**

  * For the USCDI Medication Administration data element, we added a new [US Core MedicationAdministration Profile](StructureDefinition-us-core-medicationadministration.html) that sets minimum expectations for recording, searching, and fetching the event of a patient consuming or otherwise being given a medication. `MedicationAdministration.status`, `MedicationAdministration.statusReason`, `MedicationAdministration.medication[x]`, `MedicationAdministration.subject`, `MedicationAdministration.effective[x]`, `MedicationAdministration.performer.actor`, `MedicationAdministration.request`, `MedicationAdministration.dosage.text`, `MedicationAdministration.dosage.route`, and `MedicationAdministration.dosage.dose` are *Must Support* elements, with `MedicationAdministration.effective[x]` a *Must Support* choice of `dateTime` and `Period` and the [US Core Patient Profile](StructureDefinition-us-core-patient.html) and [US Core Practitioner Profile](StructureDefinition-us-core-practitioner.html) as *Must Support* `MedicationAdministration.subject` and `MedicationAdministration.performer.actor` targets. The medication terminology matches the [US Core MedicationRequest Profile](StructureDefinition-us-core-medicationrequest.html) and the [US Core MedicationDispense Profile](StructureDefinition-us-core-medicationdispense.html), and neither of those profiles changed. `MedicationAdministration.statusReason` also addresses the USCDI Reason Not Performed data element. The [Medication List](medication-list.html) guidance for accessing a patient's medications is unchanged and remains based on MedicationRequest. **Note that the `MedicationAdministration.statusReason` binding is provisional, pending the review of the terminology aligned with the HL7 FHIR US Quality Core Implementation Guide.**

  * For the USCDI Medical Device Order data element, we added a new [US Core DeviceRequest Profile](StructureDefinition-us-core-devicerequest.html) that sets minimum expectations for recording, searching, and fetching an order for a medical device for a patient. `DeviceRequest.status`, `DeviceRequest.intent`, `DeviceRequest.code[x]`, `DeviceRequest.subject`, `DeviceRequest.authoredOn`, and `DeviceRequest.requester` are *Must Support* elements, with `DeviceRequest.code[x]` a *Must Support* choice of `CodeableConcept` and `Reference(US Core Device Profile)`, and the [US Core Patient Profile](StructureDefinition-us-core-patient.html) and [US Core Practitioner Profile](StructureDefinition-us-core-practitioner.html) as *Must Support* `DeviceRequest.subject` and `DeviceRequest.requester` targets. Because `DeviceRequest.code[x]` is a choice, a Server supports at least one of `DeviceRequest.codeCodeableConcept` and `DeviceRequest.codeReference` and a Client supports both. Guidance notes that a medical device order might instead be represented with the [US Core ServiceRequest Profile](StructureDefinition-us-core-servicerequest.html) or the [US Core MedicationRequest Profile](StructureDefinition-us-core-medicationrequest.html), depending on whether the request is procedure focused or medication related. **Note that the `DeviceRequest.codeCodeableConcept` binding is strengthened from the base FHIR *example* to *preferred* rather than naming a required vocabulary; HCPCS was considered and declined, since durable medical equipment orders are often descriptive and USCDI names no vocabulary standard for this data element.**

  * For the USCDI Nutrition Order data element, we added a new [US Core NutritionOrder Profile](StructureDefinition-us-core-nutritionorder.html) that sets minimum expectations for recording, searching, and fetching an oral diet order for a patient. `NutritionOrder.status`, `NutritionOrder.intent`, `NutritionOrder.patient`, `NutritionOrder.dateTime`, `NutritionOrder.orderer`, `NutritionOrder.oralDiet`, and `NutritionOrder.oralDiet.type` are *Must Support* elements, with the [US Core Patient Profile](StructureDefinition-us-core-patient.html) and [US Core Practitioner Profile](StructureDefinition-us-core-practitioner.html) as *Must Support* `NutritionOrder.patient` and `NutritionOrder.orderer` targets, and `NutritionOrder.oralDiet.instruction` as an *Additional USCDI* element. The profile constrains only the oral diet, so no element of `NutritionOrder.supplement` or `NutritionOrder.enteralFormula` is *Must Support*. Guidance notes that a nutrition order might instead be represented with the [US Core ServiceRequest Profile](StructureDefinition-us-core-servicerequest.html) or the [US Core MedicationRequest Profile](StructureDefinition-us-core-medicationrequest.html) depending on context, that providing the diet is recorded with the [US Core Procedure Profile](StructureDefinition-us-core-procedure.html), and that findings about what a patient has eaten are recorded as nutrition assessments on the [Screening and Assessments](screening-and-assessments.html) page. **Note that the `NutritionOrder.oralDiet.type` binding to the FHIR Diet Type value set is strengthened from the base FHIR *example* strength to *preferred*. That value set selects the SNOMED CT descendants of 182922004 (Dietary regime). These value sets are expected to move from the FHIR specification to the HL7 Terminology (THO), and US Core will use the THO value set as the preferred binding if it is published before this guide is published.**

  * For the USCDI Diagnostic Imaging Reference data element, we added a new [US Core ImagingStudy Profile](StructureDefinition-us-core-imagingstudy.html) and marked elements on two existing profiles as *Additional USCDI* elements. The new profile is deliberately slim and sets minimum expectations only for the information needed to locate or access a diagnostic imaging study: `ImagingStudy.identifier`, `ImagingStudy.status`, `ImagingStudy.subject`, and `ImagingStudy.endpoint` are *Must Support* elements, with the [US Core Patient Profile](StructureDefinition-us-core-patient.html) as the *Must Support* `ImagingStudy.subject` target. `ImagingStudy.identifier` is sliced into an accession number slice, which is *Must Support*, and a DICOM Study Instance UID slice, which is neither mandatory nor *Must Support* and establishes a path for a future version. Guidance describes how an endpoint is used, since an endpoint can launch a remote picture archiving and communication system (PACS) or viewer, provide a patient- or provider-accessible viewer, or enable transfer and retrieval, and the receiving system is not assumed to contain a viewer itself. Neither `ImagingStudy.series` nor `ImagingStudy.modality` is constrained. On the [US Core DiagnosticReport Profile for Report and Note Exchange](StructureDefinition-us-core-diagnosticreport-note.html) we added `DiagnosticReport.identifier`, `DiagnosticReport.basedOn`, `DiagnosticReport.imagingStudy`, and `DiagnosticReport.media.link` as *Additional USCDI* elements, with the new [US Core ImagingStudy Profile](StructureDefinition-us-core-imagingstudy.html) and the [US Core ServiceRequest Profile](StructureDefinition-us-core-servicerequest.html) as *Must Support* reference targets. `DiagnosticReport.media` and `DiagnosticReport.media.link` were *Must Support* before version 8.0.0 and return here as *Additional USCDI* elements. Guidance states that the reference to an ImagingStudy, with its endpoint information, is the principal mechanism for meeting this data element, and that supporting `DiagnosticReport.media.link` is not a substitute for meeting it. On the [US Core ServiceRequest Profile](StructureDefinition-us-core-servicerequest.html) we added `ServiceRequest.identifier` as an *Additional USCDI* element, because an imaging accession number originates with the order and is what ties the order, the report, and the imaging study together. The search API adds `patient + identifier` as **SHALL** for ImagingStudy and **SHOULD** for DiagnosticReport and ServiceRequest, so a known accession or business identifier can be used to locate the corresponding study, report, or order.

  * For the USCDI Accommodation data element, we added a new [US Core Patient Accommodation Profile](StructureDefinition-us-core-patient-accommodation.html), an Observation that records the supports and services a patient needs in order to access care, such as a sign language interpreter, a wheelchair-accessible room, or a sensory accommodation. `Observation.status`, `Observation.category`, `Observation.code`, `Observation.subject`, `Observation.effective[x]`, and `Observation.value[x]` are *Must Support* elements, with the [US Core Patient Profile](StructureDefinition-us-core-patient.html) as the `Observation.subject` target and `Observation.performer` an *Additional USCDI* element. `Observation.value[x]` is a *Must Support* choice of `valueCodeableConcept` and `valueString`, so a Server supports at least one and a Client supports both. We added a new category code, "accommodation", to the [US Core Category](CodeSystem-us-core-category.html) code system for `Observation.category`. Guidance states that an accommodation records what a patient needs in order to access care, not the patient's disability or functional status, which are recorded as assessments on the [Screening and Assessments](screening-and-assessments.html) page. The design team considered reusing the Simple Observation Profile within the Screening and Assessments framework and discarded it as confusing and as breaking the assessments pattern. **Note that the terminology for this data element is outstanding in two places. `Observation.code` is fixed to the placeholder code 55555-5, which is not a real LOINC code; the design team settled on a new prerelease LOINC code for "Accommodation Need" that has not been issued yet, so validation reports the code as unknown until it is replaced. `Observation.value[x]` carries no binding, because PACIO and Gravity are developing a strawman value set in VSAC. As the terminology matures, US Core will consider removing the free-text option.** This profile is the first in the guide marked *Incompatible* with IPS, which represents the same information with Flag rather than Observation.

  * For the USCDI Adverse Events data class, which is new in USCDI v7 and comprises the *Adverse Event Condition* and *Adverse Event Outcome* data elements, we added a new [Adverse Events: Clinical Records and Patient Safety Reporting](adverse-events.html) guidance page. US Core does not define an AdverseEvent profile and does not use the FHIR AdverseEvent resource. The information the two data elements describe is already recorded by existing US Core Profiles, and the new page documents which ones and why. *Adverse Event Condition* is recorded by the [US Core AllergyIntolerance Profile](StructureDefinition-us-core-allergyintolerance.html), [US Core Immunization Profile](StructureDefinition-us-core-immunization.html), both Condition profiles, [US Core DocumentReference Profile](StructureDefinition-us-core-documentreference.html), [US Core Simple Observation Profile](StructureDefinition-us-core-simple-observation.html), and [US Core Procedure Profile](StructureDefinition-us-core-procedure.html); *Adverse Event Outcome* is recorded by those and additionally by the [US Core Encounter Profile](StructureDefinition-us-core-encounter.html) and [US Core CarePlan Profile](StructureDefinition-us-core-careplan.html). Each of those profile pages gains a bullet pointing at the new page. Two points drive the guidance. First, **adverse events are recorded as ordinary clinical events and are not tagged as adverse events**, so implementers should not expect a flag, a category code, or a dedicated resource; deciding that an event was adverse, and that a clinical intervention caused it, is a judgment made elsewhere. Second, USCDI v7 scopes this data class to the clinical record and explicitly excludes patient safety analyses, internal risk management documentation, patient safety work products as defined under the Patient Safety and Quality Improvement Act of 2005, and Patient Safety Organization investigations, safety reviews, and facility-level reporting. US Core follows that boundary, which is what the page title distinguishes. The data class is not limited to immunizations and medications, although USCDI notes it includes at least those. No new profile, extension, value set, or example was added for this data class. **Note that this guidance page is a draft for this ballot. Further editing and examples are still pending.**
